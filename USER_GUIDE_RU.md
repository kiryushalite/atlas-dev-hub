# Atlas Dev Hub: подробная инструкция

Этот документ можно целиком перекинуть в обычный ChatGPT, чтобы он разъяснил тебе workflow человеческим языком.

## 1. Что такое Atlas Dev Hub

Atlas Dev Hub - это отдельное локальное приложение для разработки и оркестрации агентов.

Важно:

- `atlas-v0` - это сам продукт Atlas, над которым мы работаем.
- `atlas-dev-hub` - это пульт управления разработкой, не сам Atlas.
- Codex остаётся ведущим разработчиком и финальным интегратором.
- Claude работает как worker/reviewer: может делать отдельные ветки, ревью, UI-комментарии.
- Kimi и Perplexity подключаются как исследовательские помощники через API.
- Все серьёзные изменения идут через git-ветки/worktree, чтобы агенты не ломали один и тот же каталог.

## 3. Как теперь работать

Новый основной сценарий:

1. Открыть `Atlas Dev Hub`.
2. В `Task Inbox` написать задачу.
3. Выбрать агентов:
   - `Codex` - основной исполнитель или планировщик.
   - `Claude` - ревью, UI, альтернативная реализация, комментарии.
   - `Kimi` - длинный контекст, разбор больших идей.
   - `Perplexity` - свежие источники, документация, research.
4. Выбрать режим:
   - `work` - агент может менять файлы в своей ветке.
   - `review` - агент смотрит и комментирует.
   - `plan` - агент только планирует.
5. Нажать `Start Selected`.
6. Смотреть `Agent Status`, `Events`, `Run Log`.
7. После результата ведущий Codex проверяет ветку, тесты, diff и только потом мержит.

Короткая формула:

```text
Dev Hub = дать задачу -> агенты работают в ветках -> смотрим логи/diff -> Codex интегрирует -> Atlas двигается дальше.
```

## 4. Роли агентов

### Codex

Главная роль:

- ведущий разработчик;
- разбивает работу;
- запускает проверки;
- принимает финальное решение;
- мержит только проверенные изменения.

В Dev Hub Codex запускается через найденный локальный CLI:

```text
C:\Users\yu9lite\AppData\Local\Packages\OpenAI.Codex_2p2nqsd0c76g0\LocalCache\Local\OpenAI\Codex\bin\codex.exe
```

Ограничение на сейчас:

- этот чат Codex всё ещё нужен как живой ведущий канал;
- Dev Hub уже может запускать фоновые Codex-задачи;
- полноценный интерактивный Codex-чат внутри Dev Hub появится позже, когда будет стабильный CLI/API-режим для такого встраивания.

### Claude

Лучше всего использовать для:

- ревью архитектуры;
- UI/UX замечаний;
- поиска рисков;
- параллельной реализации маленького участка;
- проверки diff перед merge.

Claude запускается через `claude` CLI и работает в отдельной ветке.

### Kimi

Лучше всего использовать для:

- длинных контекстов;
- больших обзоров;
- второго мнения по архитектуре;
- разбора больших документов и планов.

В Dev Hub Kimi пока не редактирует файлы напрямую, а отвечает как API-помощник.

### Perplexity

Лучше всего использовать для:

- свежей документации;
- проверки текущих API;
- research с источниками;
- поиска внешних решений.

В Dev Hub Perplexity тоже пока отвечает как API-помощник.

## 5. Режимы задач

### work

Использовать, когда надо реально менять код.

Пример:

```text
Добавь в Atlas Dev Hub панель live diff для текущей agent-ветки. Не трогай provider config. После изменений запусти npm run build и cargo check.
```

### review

Использовать, когда надо проверить без изменений.

Пример:

```text
Проверь ветку agent/claude-ui-panel на риски, сломанные сценарии и пропущенные тесты. Файлы не меняй.
```

### plan

Использовать, когда надо подумать и разложить работу.

Пример:

```text
Составь план, как добавить live preview UI и git diff viewer в Atlas Dev Hub без ломки текущей архитектуры.
```

## 6. Usage Guard 70-80%

В Dev Hub есть `Usage Guard`.

Смысл:

- если текущая сессия/лимит близко к 70-80%, тяжёлые work-задачи лучше не стартовать;
- оставляем запас на визуальные правки, синтаксис, аварийные фиксы и завершение текущей работы;
- при высоком usage используем `plan` или `review`, а не `work`.

Сейчас guard ручной/консервативный, потому что не все провайдеры дают программный доступ к usage из подписки. Но рабочее правило такое:

```text
До 70% - можно делать обычную работу.
70-80% - только лёгкие правки, ревью, планы.
80%+ - сохраняем контекст, не стартуем большие задачи.
```

## 7. Как подключить Kimi

Официальная Kimi API-платформа работает через Moonshot API.

1. Открыть:

```text
https://platform.kimi.ai/
```

или консоль Moonshot/Kimi API, куда ведёт платформа.

2. Создать API key.

3. В Dev Hub открыть блок `Connections`.

4. В строке `kimi` заполнить:

```text
API key:  твой ключ Kimi/Moonshot
model:    kimi-k2.5
baseUrl:  https://api.moonshot.ai/v1
```

5. Нажать `Save`.

6. Проверить через `Research Prompt` -> `Ask Kimi`.

Если модель изменилась, можно поменять `model` вручную. По официальной документации Kimi использует OpenAI-compatible формат, `base_url` для SDK: `https://api.moonshot.ai/v1`, а прямой endpoint: `https://api.moonshot.ai/v1/chat/completions`.

## 8. Как подключить Perplexity

1. Открыть:

```text
https://docs.perplexity.ai/
```

2. Перейти в API / API keys.

3. Создать `PERPLEXITY_API_KEY`.

4. В Dev Hub открыть блок `Connections`.

5. В строке `perplexity` заполнить:

```text
API key:  твой Perplexity API key
model:    sonar
baseUrl:  https://api.perplexity.ai
```

Можно также попробовать:

```text
model: sonar-pro
```

6. Нажать `Save`.

7. Проверить через `Research Prompt` -> `Ask Perplexity`.

По официальной документации Perplexity Sonar совместим с OpenAI Chat Completions, а `base_url` для OpenAI-compatible клиента: `https://api.perplexity.ai`.

## 9. Где хранятся ключи

Ключи Kimi/Perplexity не кладутся в git-репозиторий.

Они сохраняются локально:

```text
%LOCALAPPDATA%\AtlasDevHub\providers.json
```

Важная пометка:

- v0 пока не шифрует этот файл;
- не коммитить его;
- не отправлять скриншоты с ключами;
- позже надо добавить Windows Credential Manager или шифрование.

## 10. Как смотреть работу агентов

В Dev Hub есть:

- `Agent Status` - ветки, worktree, запущенные процессы.
- `Events` - общая лента событий.
- `Run Log` - лог конкретного запуска по `RUN_ID`.
- `Provider Notes` - ответы Kimi/Perplexity.

Когда агент стартует, в `Run Log` появляется запусковый вывод, где есть:

```text
RUN_ID=...
PID=...
BRANCH=...
WORKTREE=...
LOG=...
REPORT=...
```

`RUN_ID` можно вставить в поле `Run Log` и нажать `Load`.

## 11. Как агенты не мешают друг другу

Каждая работа создаёт:

- отдельную git-ветку;
- отдельный worktree;
- свой `TASK.md`;
- свой лог в `.agent-runs`.

Это значит:

- Codex и Claude не должны одновременно править один и тот же основной каталог;
- они работают рядом, но не в одном месте;
- merge делается только после проверки;
- если ветки конфликтуют, решает ведущий Codex.

## 12. Как формулировать хорошие задачи

Хорошая задача:

```text
Цель: добавить панель live diff в Atlas Dev Hub.
Файлы/зона: atlas-dev-hub frontend, без изменения Atlas.
Ограничения: не хранить секреты в логах, не менять provider API.
Проверки: npm run build, cargo check.
Финальный отчёт: что изменено, какие риски, что проверить руками.
```

Плохая задача:

```text
Сделай всё красиво и умно.
```

Лучше давать:

- цель;
- границы;
- какие агенты участвуют;
- что считать готовым;
- какие проверки обязательны.

## 13. Как переехать в Dev Hub как в основной рабочий центр

Новый порядок:

1. Этот чат Codex использовать как ведущую стратегическую линию, пока интерактивный Codex не встроен полностью.
2. Все конкретные задачи запускать через Dev Hub.
3. В Dev Hub сначала использовать `plan`, если задача большая.
4. Потом запускать `work` для Codex или Claude.
5. Kimi/Perplexity использовать как research/review, а не как прямых редакторов файлов.
6. После результата смотреть `Run Log`, `Events`, `Agent Status`.
7. Просить Codex проверить и смержить только после успешных проверок.

Цель следующего этапа:

```text
Добавить в Dev Hub полноценный UI для diff, file changes, process tree, live preview и self-editing workflow.
```

Тогда Dev Hub станет ещё ближе к полноценной IDE-оркестраторской панели.
